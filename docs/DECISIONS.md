# Decisions

Defaults chosen while building, with the reason and how to change them. Newest last within each
phase. Format: **decision** — why — how to revisit.

## Phase 1 — skeleton

### Hardware reality check
The build machine is a **Raspberry Pi 4 Model B (4 GB) running Ubuntu 26.04 + GNOME**, not a Pi 5
on Raspberry Pi OS, and the panel is on HDMI (no DSI Touch Display 2 detected). Everything is
written to work on both: the kiosk launcher supports GNOME (XDG autostart) and labwc (Pi OS), the
audio stack uses plain ALSA tools, and the UI's renderer drops quality automatically on the weaker
Pi 4 GPU. Nothing assumes Pi-5-only features.

### Toolchain: uv workspace + pnpm workspace
Python 3.12 (pinned in `.python-version`; uv fetches it if the OS ships something else — Ubuntu 26.04
ships 3.14, for which some audio/ML wheels like onnxruntime lag). One `uv.lock` for all Python
services; one `pnpm-lock.yaml` for all frontends. Toolchains install user-locally (`~/.local`), so
only apt packages need sudo.

### Protocol: pydantic is the source of truth
`packages/protocol/src/jarvis_protocol/events.py` defines every event as a frozen pydantic model in
a discriminated union on `type`. `make protocol` exports JSON Schema and generates TypeScript with
`json-schema-to-typescript`; CI (`make protocol-check`) fails if the generated files drift. Fields
with defaults are marked required in the serialization schema because the server always sends them,
which keeps the TS union narrowable. Extra fields are rejected (`extra="forbid"`).

Events beyond the required minimum: `hello`, `status.update`, `listen.level` (mic level for the
core), `listen.end` (endpointing result), `agent.confirm_request`, `agent.progress`, `tts.sentence`
(subtitles), `playback.done` (node finished playing — the brain uses this, not `tts.end`, to open
the follow-up window), `node.command`, `ui.command`, `ui.snapshot`.

### Audio on the wire: binary frames with a stream id
Binary WebSocket frames are `uint32 LE stream_id + PCM s16le mono`. Mic audio is 16 kHz; TTS audio
uses the sample rate announced in `tts.start`. The node drops frames for any stream other than the
current one, so barge-in can't play stale audio that was already in flight.

### The brain owns the state machine
`IDLE → WAKE → LISTENING → THINKING → (TOOL) → SPEAKING → FOLLOW_UP → IDLE`, any → `ERROR → IDLE`.
It lives in `jarvis_protocol.state_machine` (pure, exhaustively tested) and the brain drives it. Edges
added beyond the spec, each for a real path: `IDLE → LISTENING` (tap-to-talk skips WAKE),
`THINKING → LISTENING` (confirmation questions and barge-in while thinking),
`THINKING → FOLLOW_UP` (empty reply), `FOLLOW_UP → WAKE` (wake word during the window),
`SPEAKING → THINKING/TOOL` (multi-step agent turns that speak between tool calls).

### Network binding
Every listener binds to `127.0.0.1` or a Tailscale address (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`);
the brain refuses to start otherwise (`settings.is_safe_bind`), wildcards included. Containers use
host networking, so the same guard applies inside Docker. The kiosk UI server binds to
`127.0.0.1` only.

### WebSocket auth
The audio node and kiosk present a shared device token (`JARVIS_NODE_TOKEN`, generated by
`make env`): `Authorization: Bearer` for the node, `?token=` for the browser (browsers can't set
WebSocket headers). `/ws/ui` also checks `Origin` against `UI_ORIGINS`. An empty token is accepted
only when `JARVIS_ENV=dev`. The token reaches the browser via `/config.json` served by the
localhost-only UI server — it's never baked into the build.

### UI rendering: raw Three.js shaders, no post-processing
The core is an icosphere with simplex-noise vertex displacement, fresnel rim and flowing filaments in
the fragment shader; "bloom" is an additive halo billboard with analytic falloff, not an
`UnrealBloomPass` (a full-screen blur chain is too expensive on the Pi GPU). All passes use ONE/ONE
premultiplied blending with alpha = brightness, so the transparent canvas composites cleanly over
the CSS vignette.

Quality presets (`high`/`medium`/`low`: mesh detail, noise octaves, particle count, frame cap,
pixel ratio). In `auto` mode the renderer measures fps over 3 s windows and only ever steps *down*
(high→medium below 50 fps, medium→low below 40), so it can't oscillate. `low` caps at 30 fps.
Per-frame values (audio levels, easing) bypass React entirely.

Night mode and screen sleep are one black overlay (no CSS filters over the canvas); when asleep the
renderer stops drawing. The panel itself isn't powered off — that needs compositor-specific DPMS
control; revisit if burn-in or power matters.

### Kiosk UI served by a 60-line Python server
`deploy/ui-server.py` serves `apps/ui/dist` on `127.0.0.1:8080` with an SPA fallback and a runtime
`/config.json` (brain URL + token from `.env`). No nginx, no Node at runtime. The brain can also
serve the UI itself (`JARVIS_UI_DIST`) when you'd rather open it from another machine.

### Deployment: docker compose for every service
One `compose.yaml` at the repo root runs everything; profiles pick what runs on a host
(`COMPOSE_PROFILES`: `brain`, `pi` = ui + audio-node, `qdrant`). One Pi = `brain,pi`; moving the
brain = `brain` on the GPU box, `pi` on the Pi, and point `BRAIN_URL` at it. Containers restart at
boot (`restart: unless-stopped`); only the kiosk *browser* runs on the host, because it needs the
desktop session.

- **Host networking** for jarvis services rather than published ports: binding stays controlled by
  `.env` + the bind guard (a published `${IP:-}:8000` silently becomes `0.0.0.0` when the variable is
  empty), and the kiosk/audio node reach `127.0.0.1` naturally.
- **Audio in a container**: the node runs as the desktop user's uid and talks to PipeWire through its
  Pulse socket (`/run/user` bind-mounted with `rslave` propagation, so a container that starts before
  the desktop login still sees the socket appear). `/dev/snd` is mapped as a raw-ALSA fallback. The
  mic loop retries with backoff if the device isn't there yet.
- **Models baked into images** (wake word/VAD in the audio-node image) so a cold boot needs no
  internet. Piper/Whisper models for the brain download once into the `jarvis-data` volume.
- `make dev-*` still runs services natively for development.

## Phase 2 — voice loop

### Audio I/O through `arecord` / `aplay`
No PortAudio on the box, and alsa-utils is everywhere. Killing `aplay` is the fastest stop for
barge-in. Playback is paced in real time with a ~160 ms lead (`PLAYBACK_LEAD_MS`) so the OS pipe never
holds seconds of audio; `tts.audio_level` is computed from the PCM being written and scheduled for
the moment it becomes audible, so the core pulses with the voice rather than ahead of it.

### Wake word + VAD on the node; endpointing decided locally
openWakeWord's ONNX backend with the bundled `hey_jarvis` model (≈21 ms per 80 ms chunk on the Pi 4),
Silero VAD via openWakeWord's bundled ONNX model (≈4 ms per chunk) — no torch. `tflite-runtime`
(declared by openWakeWord on Linux, no 3.12 wheels) is excluded via `tool.uv.exclude-dependencies`.
Endpointing (`Endpointer`) is a pure class: speech starts after 2 consecutive speech chunks, ends
after 700 ms below threshold (with 0.7× hysteresis once talking), 30 s cap, 6 s no-speech timeout.
On the wake word the node starts capturing immediately and stops any playback itself, then informs
the brain — no network round trip on the critical path. Follow-up captures send ~320 ms of pre-roll
because speech is detected a few chunks late; wake-word captures don't (the pre-roll *is* the wake
word).

### STT chain: Deepgram → OpenAI → remote Whisper → local Whisper
Configurable order in admin; engines without credentials are skipped. The chain buffers the full
utterance, so a streaming engine dying mid-sentence falls back to batch transcription of the same
audio (no "please repeat"). "faster-whisper on a tailnet GPU box" is just the OpenAI-compatible
adapter pointed at a faster-whisper server (e.g. speaches) — no bespoke protocol. Local
`tiny.en` (int8) is the last resort: ~3.4 s for a short sentence on the Pi 4 CPU — slow, but it works
with the internet cable pulled.

### TTS chain: OpenAI (fable + butler instructions) → ElevenLabs (George) → Piper (alan, en_GB)
Engines are swapped only before the first byte of a sentence, never mid-sentence, and once a reply
falls back it keeps that voice to the end. Cloud engines get 6 s to start; local ones 30 s (model
load). Mixed sample rates within one reply are resampled to the stream's rate. Piper and Whisper
are pre-loaded at brain start (`JARVIS_WARM_LOCAL_VOICE`) so an offline fallback is immediate.
Using any non-primary engine raises the UI's "offline voice" badge.

### Sentence streaming
`SentenceSplitter` releases the first sentence as soon as it is complete (it decides
time-to-first-audio); sentences that arrive together after that are merged up to ~200 chars for
better prosody, never into the first one. Abbreviations and decimals don't split. Markdown, lists
and URLs are stripped before speaking.

### The follow-up window waits for real playback
The brain opens the 8 s follow-up window when the node reports `playback.done`, not when it
finished *sending* audio (which is seconds earlier). The node then waits for actual speech before
announcing `listen.start`, so silence in the window never produces an empty turn.

### Known gaps (tracked)
- Wake threshold / chime / VAD timings from the admin Voice page must reach the node: the node
  reads `.env` today; a `node.config` push arrives with the admin panel (phase 4).
- Docker images could not be built on the dev Pi (no Docker daemon, no sudo); the compose file is
  validated with `docker compose config`, and CI builds the images.

## Phase 3 — conversation

### Provider interface and the agent loop
`Provider.run(messages, tools, *, stream) -> AsyncIterator[AgentEvent]` (text deltas, tool-call
requests, progress, completion with usage/cost). Messages use a neutral format; assistant turns can
carry provider-native `raw` content that is replayed only to the provider that produced it. The
agent loop is ~150 lines over that interface — no framework. Max 8 steps (admin-configurable).
Failover to the next provider happens only if the current one fails **before saying anything** in
that step; once words are spoken we never restart mid-reply.

### Anthropic provider
Official `anthropic` SDK (async, `client.beta.messages.stream`), adaptive thinking (the default on
current models) with `output_config.effort` (`low` for the fast tier, `medium` for the strong tier).
No sampling parameters, no prefill (both rejected by current models). Tools stream their inputs
eagerly (`eager_input_streaming`); every input is re-validated by the tool registry before running.
Refusals (`stop_reason: "refusal"`) are spoken as a one-line decline; truncated tool calls are never
executed. **Server-side refusal fallback** (`fallbacks: "default"`, beta
`server-side-fallback-2026-07-01`) is on for models that support it (Opus 5.5) — turn it off by
pointing the strong tier at a model without it.

Prompt-cache/preserved-thinking hygiene: the persona system prompt and the tool set are frozen per
process; per-turn context (time, location, weather, summary) is an appended `role: "system"` message
after the user turn (models without mid-conversation system messages get it folded into the user
turn). Within a turn the history is append-only with thinking blocks replayed verbatim; across turns
history is stored as plain text, i.e. all earlier thinking blocks are dropped — which the API allows.

### Model tiers
Spec: "default conversation → fast model; tools/reasoning → stronger API model". Defaults:
`claude-fast` = **Claude Haiku 5.5** (`effort: low`) and `claude-strong` = **Claude Opus 5.5**
(`effort: medium`), both editable in admin. Chat route: `local → claude-fast → claude-strong`;
tools route: `claude-strong → claude-fast → local`; task route: agent CLIs (phase 8) then
`claude-strong`. Routing is a keyword classifier (word-boundary matches, lists editable in admin) —
no extra LLM call on the latency path. Note every route still exposes all tools; routing only picks
the model.

### Local / OpenAI-compatible provider
Official `openai` SDK against any OpenAI-compatible base URL (OpenAI, OpenRouter, the tailnet LLM).
`tool_mode`: `native`, `json` (tools described in the prompt; the model answers with exactly one
`{"tool", "arguments"}` object; strict parse; one corrective retry; never spoken), or `auto` (native,
switching to json permanently if the server rejects `tools`). `<think>…</think>` sections from
reasoning models are filtered out of the spoken stream. Servers that reject
`stream_options.include_usage` are retried without it.

Found on the tailnet: `spark` (100.115.124.66:8000, nginx in front of an Ollama-style server).
Measured from the Pi: `chat:latest` 0.6 s to first token warm (2.1 s after a prompt change, i.e. cold
prefix cache), native tool calls correct; `fast:latest` 7.7 s cold. `.env` points
`LOCAL_LLM_BASE_URL`/`LOCAL_LLM_MODEL` at `spark` / `chat:latest` — confirm or change.

### Health, fallback, "says so"
Every provider is health-checked every 30 s (`/models` for OpenAI-compatible servers,
`models.retrieve` for Anthropic — no tokens spent). Chains are ordered known-healthy → unknown →
known-unhealthy. A runtime failure marks the provider unhealthy immediately. When the turn ends up on
a local provider because the preferred one is down, Jarvis prefixes the reply once per degraded
period: "I'm running on the local model for now". Each call logs provider, model, route, time to
first token, total time, tokens and cost.

### Short-term memory
Rolling window of the last 12 exchanges as plain text; when it overflows, the oldest half is
summarised in the background by the chat route (never on the latency path) and the summary rides in
the per-turn context note. After 30 minutes of silence the conversation starts fresh.

### Measured (Pi 4, offline path: local Whisper → spark `chat:latest` → Piper)
"Hey Jarvis… what time is it?" → "It's twenty past one in the morning." End of speech → first audio
5.8–6.7 s, of which ~3 s is faster-whisper `tiny.en` on the Pi CPU and ~2 s a cold LLM prefix. The
< 1.5 s target needs streaming cloud STT (Deepgram finalises in ~0.3 s) or a GPU Whisper; spark has no
`/v1/audio/transcriptions` endpoint today. Running
[speaches](https://github.com/speaches-ai/speaches) (faster-whisper, OpenAI-compatible) on spark and
setting Voice → `whisper_remote_url` would make the offline path fast too.

## Phase 4 — admin panel

### Admin auth: password + TOTP (not Tailscale identity headers)
Tailscale identity headers only exist behind `tailscale serve`, which would add a moving part and
tie auth to one ingress. Instead: a single admin account, password hashed with scrypt (stdlib, no
native deps), first password from `ADMIN_BOOTSTRAP_PASSWORD` (generated by `make env`), TOTP set up on
first login and then mandatory (secret encrypted with `JARVIS_SECRET_KEY`). Password-only sessions
can do nothing but finish TOTP setup. Sessions: 256-bit random token in an HttpOnly
SameSite=Strict cookie, only its SHA-256 stored, 12 h sliding expiry, all sessions revoked on
password change. CSRF: SameSite=Strict **plus** a required `X-Jarvis-Admin: 1` header on every
mutating request. Login failures are rate limited per IP (5 per 5 min → 1 min lockout). Strict CSP
(`default-src 'self'`), `X-Frame-Options: DENY`, no-store on API responses. Secrets are write-only
through the API. The admin app is a separate FastAPI app on its own port and never linked from the
kiosk; `ADMIN_HOST` obeys the same loopback/Tailscale bind guard.

### Same process, separate app
The admin API runs in the brain process (second uvicorn server) so it sees live state — current
state, provider health, the event bus — without another IPC layer. It is still a separate ASGI app,
port and frontend.

### Traces
Every turn is stored in SQLite (last 2000): user text, reply, provider/model, tokens, cost, the
traced protocol events (no levels/tokens), tool calls with timings, and per-stage latencies
(`wake→listen`, `STT`, `LLM first token`, `TTS first audio`, `end of speech → first audio`). The
overview shows p50/p90 over the last 50 turns.

### Live voice tuning reaches the node
New protocol events: `node.config` (brain → node: wake threshold, chime, VAD end silence, max
utterance, monitor) sent on connect and whenever the Voice config changes; `wake.score` (node →
brain while monitoring). Monitor mode streams mic level and the best wake score so the admin page can
show a live meter and a "test wake" check.

## Phase 5 — tools, MCP, skills, confirmations

### Tool names on the wire
Anthropic and OpenAI only accept `^[a-zA-Z0-9_-]{1,64}$`, so the spec's `mcp.<server>.<tool>` is
sent as `mcp__<server>__<tool>` and shown as `mcp.<server>.<tool>` in admin; likewise
`memory_remember`/`memory_recall`, `skill__<skill>__<script>`.

### Confirmation flow (no exceptions)
An `irreversible` tool call is never executed in the turn that requested it. The agent stops,
speaks a read-back built from the tool's `describe(args)` ("Just to confirm, I'm about to delete
your note 'wifi password…'. Shall I go ahead?"), publishes `agent.confirm_request`, and the follow-up
window opens. The next utterance is matched against strict yes/no patterns: **yes** executes the call
and the model continues from the saved, append-only transcript (tool result appended right after its
own tool call — valid for preserved thinking); **no** replies "Okay, I won't." without an LLM call;
**anything else** ("actually send it to Bob") drops the pending action and is handled as a new
request. Pending confirmations expire after 60 s. Admin overrides can only *raise* a tool's
side-effect level, never lower it; `_run_tool` refuses unconfirmed irreversible calls as a second
line of defence. Reversible/safe calls in the same step run before the irreversible one.

### Built-in tools
`get_time`, `weather` (Open-Meteo, no key), `web_search` (Brave → Tavily → SearXNG → DuckDuckGo HTML,
whichever is configured; DuckDuckGo needs no key), `read_url` (trafilatura/pypdf text extraction),
`read_file`/`list_files` (one allowed folder, `data/files` by default; txt/md/pdf/docx),
`notes_add/list/search/delete` (SQLite FTS5), `timer_set`, `reminder_set`, `timers_list`,
`timer_cancel` (persisted; announced with a chime when due, then a follow-up window),
`memory_remember`/`memory_recall` (long-term facts, separate from documents). Built-in tools declare
their side effects in code; connectors and skills declare theirs in `manifest.yaml`.

**SSRF guard**: `read_url` is driven by the model and web pages can carry prompt injections, so it
refuses loopback, private, link-local, CGNAT/Tailscale and other non-public targets — checked on every
redirect hop — unless `tools.url_allow_private` is set. (DNS rebinding between check and connect is
a known residual risk; acceptable for v1.) DOCX parsing disables XML entities.

### MCP client
Official `mcp` SDK (2.x) high-level `Client`: stdio (command + args + env) and streamable HTTP (URL +
headers). Each server runs in its own task with backoff reconnects; config changes restart only the
changed servers; tools register/unregister live. Env and header values support `${SECRET_NAME}`
references resolved from the encrypted secret store; stdio servers inherit only PATH/HOME/LANG/TZ.
Default side effect from MCP annotations: `readOnlyHint` → none, `destructiveHint: false` →
reversible, anything else → **irreversible** (unknown tools need confirmation). Per-tool levels and an
allow-list are set per server in admin.

### Skills
`skills/<name>/SKILL.md` (frontmatter: name, description, triggers). Only the catalog (name,
description, triggers) is in the prompt, inside the `skill_load` tool description; full instructions
load on demand. Scripts become one tool each so each has its own side-effect level from the skill's
`manifest.yaml` — undeclared scripts are irreversible. Scripts run with a timeout, a minimal env plus
the manifest's required secrets, and a private working directory. Hot reload via `watchfiles`; admin
can upload a zip (zip-slip and size checked), edit files, enable/disable and delete.

### Local model reality check (measured on spark)
With ~20 tools, `chat:latest` initially *claimed* actions ("Noted.", "Deleted.") without calling the
tool and invented a morning briefing; `qwen3-next:80b` did the same; `qwen3:8b` called tools
correctly but took 7–33 s (thinking model). Nothing irreversible ever ran (the confirmation gate
held). Making the prompt explicit — actions only happen through tools, claiming otherwise is a lie,
never state what you haven't looked up — fixed `chat:latest`: notes, skill-driven briefing with real
weather, confirmation read-back with the actual note text, and real deletion, at 0.6–4 s per turn.
The tools route still prefers Claude when a key is configured.

## Phase 6 — connectors

### One folder + one manifest per connector
`connectors/<id>/{manifest.yaml, connector.py}`; discovered at start; a connector's tools are
registered only when it is enabled, its required secrets exist and (for OAuth) it is connected. The
loader refuses code that disagrees with the manifest. `connectors/_template/` (Home Assistant) is a
working copy-me example; `docs/ADDING_A_CONNECTOR.md` is the 30-minute guide.

### OAuth without Google client libraries
Authorization code + PKCE (S256) over httpx, `access_type=offline` + `prompt=consent` for a refresh
token, automatic refresh, revocation on disconnect. Tokens are stored in the encrypted secret store
(`OAUTH_TOKEN_<ID>`). The callback is reached by a cross-site redirect, so the SameSite=Strict admin
cookie isn't sent; it is authenticated by the single-use, 10-minute `state` that a signed-in admin
created (bound server-side to the PKCE verifier). Google requires https or loopback redirect URIs:
recommended path is `tailscale serve` HTTPS; fallback is a loopback redirect plus "paste the URL you
landed on".

### Gmail and Calendar scopes
Gmail: `gmail.readonly` + `gmail.compose` (search, read, draft, send). Calendar:
`calendar.events` (primary calendar; list + create). `gmail_send` and `calendar_create_event` are
irreversible with natural read-backs ("reply to sam@…, saying: On my way.", "add 'Haircut' to your
calendar tomorrow at 10:00 for an hour"); drafts are reversible. Replies keep the thread
(`threadId`, `In-Reply-To`, `References`, "Re:" subject).

### Now card
Connectors may implement `now()`; the registry merges results every 5 minutes (and right after a
connect) into the UI's Now card: next timed event in the coming week (title, start, location) and
unread-important mail from the last 7 days. A changed card is pushed with a `ui.snapshot`.

### What needs you
Google Cloud OAuth client (ID + secret) — see ADDING_A_CONNECTOR.md § OAuth redirect URI. Until
then the connectors show as "missing secrets" and their tools stay unregistered.

## Phase 7 — knowledge

### Storage: SQLite everywhere by default, Qdrant optional
Sources, chunks, BM25 (FTS5), vectors (`sqlite-vec`, loaded into the same connection) and the graph
all live in the one SQLite file — zero ops, works on the Pi, one backup. `knowledge.vector_backend:
qdrant` switches vectors to Qdrant over REST (compose profile `qdrant`) for a brain host with a big
corpus. Each vector index records its embedding model + dimension; changing the model resets the
index and admin → Knowledge → Re-index re-embeds everything (chunks and memories).

### Graph store: SQLite tables + networkx, not Kùzu
Kùzu was archived by its authors in 2025, so building on it now would mean an unmaintained native
dependency. The graph here is small (entities/relations extracted from personal documents): tables
`kb_entities` (+FTS), `kb_relations`, `kb_mentions` (entity ↔ chunk, for citations) and
`kb_communities`, with networkx Louvain for community detection. LightRAG-style: the LLM extracts up
to 12 entities/relations per chunk as JSON (chat route, so the local model does it for free);
communities of ≥ 3 entities get a title + 2–3 sentence summary (embedded for global queries).
**Local** queries find matching entities (FTS, falling back to entities mentioned in the best chunks)
and return their one-hop relations plus supporting passages; **global** queries rank community
summaries.

### Embeddings
Chain: an OpenAI-compatible embedding endpoint on the tailnet if configured (`embed_base_url` +
`embed_model` — e.g. Ollama on spark after `ollama pull nomic-embed-text`; spark has no embedding
model today and I didn't install one on your server), else in-process **fastembed**
`BAAI/bge-small-en-v1.5` (ONNX, no torch; Pi 4: 0.1 s per query, ~13 chunks/s, ~330 MB), else OpenAI
`text-embedding-3-small`. Loaded at startup so the first question isn't slow.

### Retrieval
BM25 top-N and vector top-N fused with reciprocal rank fusion (k=60). Cross-encoder re-ranking
(fastembed `ms-marco-MiniLM-L-6-v2`) is implemented but **off by default**: ~3 s per query on the
Pi 4 CPU is too slow for voice; turn it on when the brain runs on a faster host (it then re-ranks the
top 8). Results carry a citation string (title + page, or section heading) and the tool tells the
model to cite in one short phrase.

### Ingestion
Admin upload (PDF, MD, TXT, DOCX, HTML, CSV, JSON), URLs (same SSRF guard as `read_url`), pinned Gmail
threads, and a watched folder (`data/knowledge/inbox`; add/change re-ingests, delete removes). Jobs are
queued, resumed after restart, skipped when content is unchanged (hash), and report status
(queued → extracting → embedding → graph → ready/error). Chunks ~1100 chars with ~180 chars of
sentence-aligned overlap, keeping page numbers and the heading the chunk starts under.

### Long-term memory
Facts stay separate from documents (`memories` table, admin → Memory). Recall combines FTS with
vector similarity (threshold 0.35) when an embedder is available; admin edits re-embed.

### Measured on the Pi (real components)
`docs/ARCHITECTURE.md`: 4 chunks, 46 entities, 39 relations, 5 communities ("Pi-Based Voice Kiosk
System", …) — ingestion ~80 s, almost all of it graph extraction on spark. Hybrid search without
re-ranking is well under a second once warm.

## Phase 8 — agent-CLI providers

### Headless CLIs behind the same Provider interface
`AgentCLIProvider` implements `Provider.run`, so routing, health checks (`<binary> --version`) and
the admin Test button work the same as for model APIs. Flags were checked against each tool's
current docs/source (Nov 2026) rather than remembered:
- **Claude Code** `claude -p <task> --output-format stream-json --verbose --permission-mode acceptEdits
  --allowedTools <list> --max-budget-usd <n> --no-session-persistence [--model]` — parses
  `assistant` tool_use blocks for progress and the final `result` (text, `total_cost_usd`, usage).
- **Codex** `codex exec --json --cd <dir> --sandbox workspace-write --skip-git-repo-check --ephemeral
  [--model] <task>` — JSONL `item.started/completed` (`command_execution`, `file_change`,
  `agent_message`), `turn.completed` usage, `turn.failed`/`error`.
- **Cursor** `agent -p --output-format stream-json --force --trust --workspace <dir> [--model] <task>`
  with `CURSOR_API_KEY` from secrets — `tool_call` started/completed, `assistant`, `result`.

Each task runs in its own folder under `data/agent-work/` (configurable per provider), in its own
process group with a minimal environment, a hard timeout (30 min default) and, for Claude Code, a
dollar budget (`--max-budget-usd`, default $5). All three are **disabled by default** — enable them in
admin → Providers once the CLIs are installed and logged in on the brain host (in Docker: install them
in the brain image or run the brain natively for this).

### Background jobs, spoken confirmation, spoken summary
"Build / code / fix / run…" requests (task route) skip the chat model entirely: Jarvis reads back
"Just to confirm, I'm about to hand this to Claude Code: …. Shall I go ahead?" (the generic
irreversible-tool confirmation, via the `delegate_task` tool), and on "yes" starts a background job
and says "Claude Code is on it. I'll let you know when it's done." — the conversation stays free.
Progress ("Claude Code is editing app.py", "… is running pytest -q") streams to the kiosk as a chip
(throttled to one update per 1.5 s); on completion the report is summarised into two spoken sentences
by the chat model (falling back to its first sentences) and announced with a chime. The model can
also call `delegate_task` itself (same confirmation), `task_status` and `task_cancel`. Agent CLIs are
never used as chat models, even if listed in a chat route.

### Admin API follow-ups (from the admin UI work)
MCP env/header values are masked in `GET/PUT /api/config/mcp` (`${SECRET}` references stay visible;
saving a masked value keeps the stored one); tool overrides can be removed
(`DELETE /api/tools/{name}/override`).
